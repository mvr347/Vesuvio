# Проверка обучающих данных

Это проверка конкретных игровых фрагментов, а не список «100% чистых» игроков.
Проверенный сегодня клиент не даёт исключений из проверок завтра.

## Как работает

1. Автобан (в том числе попадание в очередь наказаний), высокий Trust и ловушка
   создают кандидатов со статусом «Ожидает проверки». Они не изменяют онлайн-веса
   и не входят в CSV для автоматического ONNX-обучения.
2. В LoveWebAdmin: **Античит → Обучающие данные**. Сотрудник выбирает отдельное
   окно и вердикт «Чит / Чистый» с обоснованием. Для подтверждения метки «Чит»
   от автобана нужен номер окончательно оформленного бана.
3. Можно выбрать несколько ожидающих окон и подтвердить чистый фрагмент.
   Все окна должны относиться к одному UUID, одному входу и известной версии
   клиента; максимальная продолжительность — 30 минут. Новые окна и следующие
   входы не подтверждаются автоматически.
4. Снятие бана (включая принятую апелляцию) или решение «Чистый» в разборе бана
   отправляет связанные метки на пересмотр. Это не превращает их автоматически
   в отрицательные примеры. Связь: `lovewebadmin:ban:<номер>`.

LoveWebAdmin хранит очередь доставки пересмотров в своей SQLite. При недоступном
античите она повторяется после подключения; повторная доставка безопасна.
Отозванное основание блокирует запоздалую форму подтверждения даже тогда,
когда апелляция пришла раньше самой метки. Старые снятые баны также сверяются.
Наказания без сохранённой связи с окнами не используются как доказательство
для автоматического размечивания всей истории игрока.

## Хранение и ограничения

`datasets/training.sqlite` содержит исходные окна, состояние, источник, UUID,
ник, идентификатор входа, версию клиента, время записи, сотрудника, обоснование,
связь с наказанием, версии решений и историю. Проверенные фрагменты хранят
отдельный список выбранных окон. Решение и его аудит сохраняются транзакционно;
устаревшая версия формы не заменяет новое решение.

`training.yml` создаётся автоматически. По умолчанию:

- не более 50 окон на игрока и тип признаков за сутки UTC;
- одно окно за 15 секунд; одинаковые векторы за сутки не повторяются;
- не более 100 последних подтверждённых окон игрока каждого типа в полной
  учебной выборке; более старые решения сохраняются в истории;
- максимум 100 000 записей. При заполнении новые окна отклоняются; лимит
  меняется администратором после оценки объёма данных, без молчаливого удаления аудита.

Ограничения действуют также для ручных `/vesuvio learn` и разбора пограничных
образцов. Суточный лимит учитывает ожидающие и отозванные записи и не сбрасывается
при перезапуске. Это ограничение вклада, а не защита от всех видов отравления
данных: разные UUID всё равно требуют качественного ручного разбора.

Ввод записей выполняется одним виртуальным работником с очередью на 128 задач.
Переполнение не переносит SQLite/CSV на серверный поток. При остановке приём
прекращается, очередь завершается либо отменяется до закрытия хранилища.

Старый `auto_dataset.csv` сохраняется для совместимости и анализа. Его импорт
не подтверждает исторические метки. Автоматический тренер получает отдельный
`staging/approved_dataset.csv` только из подтверждённой и ограниченной выборки.
Онлайн-классификаторы восстанавливаются из этой же выборки после перезапуска
и пересобираются при пересмотре. Отозванные метки не остаются в SGD-весах.

Новые ONNX-артефакты получают `.labels` с версией решений и SHA-256 модели.
Пересмотр во время переобучения запрещает публикацию устаревшего результата.
Если версия уже загруженного артефакта устарела, вычисление использует существующий
резервный путь вместо него. Метаданные следуют за теневой публикацией и резервной
копией. Старые/вручную установленные модели без метаданных нельзя задним числом
связать с конкретными окнами: их нужно заменить переобученным артефактом.

## API

Новая capability `training-governance`; старые реализации API совместимы через
методы по умолчанию. Асинхронные методы: `getTrainingWindows`,
`reviewTrainingWindow`, `verifyTrainingFragment`, `revokeTrainingReference`.
Список панели ограничен последними 200 окнами; локальные фильтры и страницы
относятся к этому срезу. Для управления нужны `MANAGE_VESUVIO` и
`VIEW_VESUVIO_ADVANCED`; связь с баном дополнительно требует `VIEW_BANS` и
проверяется на принадлежность игроку. Сотрудник берётся из сессии панели.

Автоматические тесты проверяют карантин, повторы и лимиты после перезапуска,
границы сессий/клиентов, атомарность аудита, отзыв, поздние решения, экспорт и
пересборку весов. Точность распознавания на живом сервере этим не измеряется.
